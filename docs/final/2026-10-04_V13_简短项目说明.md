# Mag 7 Earnings Radar：简短项目说明

版本：2026-10-04｜V13

## 1. 系统怎么工作

系统的数据流很简单：

**公开数据源 → 后端同步与校验 → 静态 JSON → 网页展示。**

1. Nasdaq 提供财报日期、EPS 预期和实际结果；公司 IR 用于确认正式日期和核对财报；Yahoo Finance 提供股票与 QQQ 行情；官方或聚合接口提供已公布的宏观数据。
2. Python 脚本定时抓取数据，统一公司、日期和状态格式，并区分“推算、市场预计、IR 确认、已发布”。
3. 系统计算 EPS 预期差、股票相对 QQQ 的 1 日和 5 日表现，为 77 场已发布事件生成 Preview / Analysis，并为当前 28 条未来事件生成 Preview。
4. 自动测试检查公司覆盖、日期状态、来源链接、研究结构和页面契约。测试通过后，GitHub Actions 更新 JSON 并部署 GitHub Pages。
5. 浏览器只读取已经生成的 JSON，不直接连接需要密钥的服务，也不在页面里临时编造研究结果。

AI 只在少量深度研究中使用：它把已经核验的材料压缩成更清楚的文字。常规日历、行情、宏观数据和全部基础研究不依赖 AI。

## 2. AI 与确定性逻辑如何分工

### 交给确定性逻辑

- 财报日期和状态转换；
- EPS 实际值、预期值和差值；
- 股票与 QQQ 的收益计算；
- 数据缓存、来源引用、历史回放和自动发布；
- 判断数据是否齐全、测试是否通过。

这些工作有明确答案，必须可重复、可测试、可追溯。如果交给模型，容易出现日期错误、数字失真或状态混淆。

### 交给 AI

- 在给定来源和数字范围内压缩长材料；
- 把多个已知事实组织成简洁的摘要；
- 帮助表达风险、分歧和需要继续观察的问题。

AI 不决定日期，不修改数字，不创造来源，也不能提前生成财报后的结论。这样设计是为了兼顾可读性、准确性和成本：模型负责语言，程序负责事实。

## 3. 如何继续扩展而不失控

下一阶段会把目前较集中的代码拆成几个边界清楚的模块：

- **数据连接层**：分别处理 Nasdaq、公司 IR、行情、宏观数据和原始财报；
- **统一数据层**：所有公司使用同一事件、指标、来源和状态结构；
- **研究流程层**：Preview、Analysis、风险检查和 AI 摘要各自独立；
- **展示层**：日历、公司页、图表和研究卡片拆成独立组件；
- **验证层**：每增加公司或研究步骤，都先增加数据契约和回归测试；
- **运行记录层**：保存更新时间、数据变化、失败原因和对应的自动任务链接。

原始财报会作为只读证据保存；多轮追问会放在独立会话层，不直接修改基础数据。新增 AI 能力必须接受固定输入结构、输出结构和数字校验，不能绕过现有数据流程。

核心原则是：**先定义数据和边界，再增加功能；先让结果可验证，再让表达更智能。**

## A. 一个典型 Bug

最初，完整的未来财报 Preview 只覆盖 Microsoft。AAPL 等公司虽然有日期，但前端只能显示简版模板。

原因不是页面渲染错误，而是研究生成器只处理了历史事件，并把 Microsoft 作为单独特例。修复时没有继续增加 AAPL 特例，而是建立统一的未来 Preview 生成逻辑，让全部 7 家公司、28 条未来事件使用同一结构，并增加自动测试防止再次遗漏。

## B. 一次重要的实现调整

项目早期更像一个单页演示，研究内容和页面逻辑结合较紧，也容易把 AI 当成通用解决方案。后来调整为“确定性数据流水线 + 静态研究缓存 + 可选 AI 表达”的结构。

这次调整牺牲了一些生成上的灵活性，但换来了更低成本、更清楚的失败位置，以及可以重复验证的结果。这也是系统最终被做成现在这种形态的主要原因。
